# 配置仓库的 diff 与三方合并库

我们在做配置仓库的自动化合并。git 自带的合并策略对配置文件不太合适，几个人的改动老被判成冲突，或者合出来的东西顺序乱掉。想自己写一个 diff 和合并的库，规则我们自己定。

diff 要行级的，另外还要**行内的词级差异**：一行里只改了一个数字，报出来应该是那一个词变了，而不是整行删掉再加一行。合并是**三方**的：给一份基准和两边各自的修改，能自动合就合，合不了的冲突按下面写的格式标出来，位置精确到行。性能上最大的配置文件两万多行，diff 和合并都要在几秒内完成，别写成两个文件逐行两两比较那种平方复杂度的做法。同一份输入跑两遍结果必须一模一样，等价的最小编辑脚本可能有多个，取哪个按下面写死的规则来。实现只用标准库，测试用 unittest。

仓库里只有这份说明和 samples/ 里的样例，代码从零写。

## diff 规则

**行级**：编辑只有「删除一行」和「插入一行」两种，输出必须是最小编辑脚本（编辑操作数最少）。等价的最小脚本有多个，取法写死成下面这条，保证同一份输入永远得到同一个结果：

> 先求两个文件的最长公共子序列；在**所有**最长公共子序列里取「按 base 行号逐个比较最小」的那一个（也就是优先保留靠前的匹配）。编辑脚本由「不在公共子序列里的 base 行（删除）」和「不在公共子序列里的另一侧行（插入）」构成，按文件位置排列。

小例子：base = `x a`，另一侧 = `a x`，两个长度为 1 的公共子序列分别是「base 第 1 行的 x」和「base 第 2 行的 a」，按规则取前者，所以结果是「保留 x，删除 a，插入 x」。

**实现提示（不是额外规则）**：两万行不能真去建 `n × m` 的表，用 Myers 这类 `O(编辑距离 × 行数)` 的算法即可；只要并列时的选择与上面那条规则等价就行。

**词级**：只对「被判定为替换的行」做词级 diff。词按**空白切分**（一段非空白连续字符合成一个词）。词级 diff 用同一套规则求最小编辑脚本、同样的并列取法。于是 `timeout: 30` → `timeout: 60` 的词级差异就是「删掉词 `30`、插入词 `60`」，而不是整行。

## 合并规则

三方合并的输入是 base、ours、theirs：

1. 分别算出 base→ours、base→theirs 的变更块（每个块 = base 的一段连续行被替换成另一段内容；纯插入的块不占 base 行，位置记成空区间）。
2. 两边各自独有的变更块（另一边没碰同一段）**直接合**，按 base 位置排列；
3. 两边动了**同一段** base 行时再看内容：两边替换后的内容**完全一样** → 自动合，只保留一份；不一样 → **冲突**；
4. **相邻行各改各的不算冲突**：两边改的 base 行区间只要有重叠才算撞上，紧挨着（一个改第 3 行、另一个改第 4 行）属于不相干区域，自动合；
5. **纯插入不占 base 行**：两个插入只有落在同一个位置才算撞上；插入落在被改动区间**内部**也算撞上；插在改动区间的开头或结尾（即插在被改行的前面/后面）不算冲突；
6. 只有一边动了 → 用动的那一边；两边都没动 → 保留 base。

判定顺序固定为「先按位置找有没有撞上的块 → 再看内容是否相同」，所以同一份输入结果唯一。

## 冲突标记格式

合并结果里的冲突块用下面这套标记（含公共祖先，方便人工判断）：

```text
<<<<<<< ours
<ours 在这一段的内容，可以是多行；如果 ours 是删除，这里没有行>
||||||| base
<base 在这一段的内容>
=======
<theirs 在这一段的内容>
>>>>>>> theirs
```

标记行本身左边不留空格，内容行原样保留（包括缩进）。

## 输出结构

**合并输出**（`samples/case-N/expected.txt` 就是它）：

```text
<合并后的内容，冲突按上面的标记写进去，逐行，行尾 LF>
# conflicts                       ← 只有存在冲突时才出现这一行
conflict,<base 起行>,<涉及行数>    ← 每个冲突一行，行号从 1 起
```

`涉及行数` 是冲突覆盖的 base 行数：改一行是 `1`，**纯插入冲突是 `0`**（起行写插入点后面那一行的行号；如果插在文件末尾，写 `base 行数 + 1`）。用「起行 + 行数」而不是「起行 + 止行」，是为了让纯插入这种空区间也能表示清楚。

**diff 输出**（文本渲染，供 CLI 与测试对比）：

```text
<hunk 标签>,<base 起行>,<base 行数>,<另一侧起行>,<另一侧行数>
words,<base 行号>,<另一侧行号>,<删除的词（空格分隔，可为空）>,<插入的词（空格分隔，可为空）>
```

- `hunk 标签` 只有 `equal` 与 `change` 两种；`equal` 后面不跟 `words` 行；
- `change` hunk 里**每一对位置对应的变更行**（base 的第 k 行对另一侧的第 k 行）跟一行 `words`；某一侧多出来的行，`words` 行只填那一侧；
- 行号一律 1 起；行数可以为 0（纯插入的 `base 行数` 为 0，纯删除的另一侧行数为 0）。

## 其他约定

- 输入按 `\n` 切分，只处理 LF；输出一律以 LF 结尾；空文件视为 0 行。
- 不做任何额外归一化（不 trim、不改缩进、不排序），配置文件里的顺序完全按输入来。
- 整数、字符串等具体格式差异都属于“行内容不同”，由词级 diff 呈现。
- 性能目标：两万行的 base，diff 与三方合并各不超过 **3 秒**（单线程、只算算法本身），实现复杂度不能是逐行两两比较的平方级。

## 样例

每组样例四个文件，`expected.txt` 就是验收标准：

```text
samples/case-N/base.txt     基准
samples/case-N/ours.txt     一边的修改
samples/case-N/theirs.txt   另一边的修改
samples/case-N/expected.txt 期望的合并输出（含冲突标记与冲突清单）
```

| 样例 | 场景 | 期望 |
| --- | --- | --- |
| case-1 | 两边改互不相干的区域 | 自动合，无冲突 |
| case-2 | 相邻两行各改各的 | 自动合，无冲突 |
| case-3 | 两边改成完全一样的内容 | 自动合，无冲突 |
| case-4 | 只有一边动了 | 采用动的那一边 |
| case-5 | 两边改同一行的同一位置 | **冲突**，`conflict,2,1` |
| case-6 | 同一位置各插入不同内容 | **冲突**，`conflict,3,0`（纯插入） |
| case-7 | 一边删掉某行、另一边改同一行 | **冲突**，`conflict,2,1` |
| case-8 | 行内只改一个数字 + 另一边改别处 | 自动合，无冲突（词级差异体现在 diff 输出里） |
